## 6.5 并行计算与大规模优化

### 6.5.1 为什么需要并行？

多核 CPU 已成为标配，但单线程代码只利用了其中一核。科学计算与机器学习中的**稠密矩阵乘法、批量梯度计算、蒙特卡罗模拟**天然具有**数据并行**结构——同一操作施加在大量独立数据块上。

**优化中的三类并行场景**：

1. **线性代数内核**：矩阵乘、分解等是 L-BFGS、共轭梯度等算法每步的基础操作
2. **样本级并行**：梯度 $\nabla f(\mathbf{x})=\frac{1}{n}\sum_i\nabla f_i(\mathbf{x})$ 可分块累加
3. **多起点搜索**：非凸问题从多个初值独立运行——**尴尬并行**（embarrassingly parallel）

### 6.5.2 Amdahl 定律与可扩展性

若程序中比例为 $p$ 的部分可并行，加速比上界为：
$$S(s) \leq \frac{1}{(1-p)+p/s}$$
当 $s\to\infty$ 时，上界趋于 $1/(1-p)$。**顺序瓶颈**决定了天花板——即便矩阵乘完全并行，前后不可并行的调度与归约仍限制整体加速。

**两种可扩展性**：
- **强可扩展**：固定问题规模，增加处理器数，关注加速比
- **弱可扩展**：随处理器数同步增大问题规模，关注每处理器负载是否恒定

### 6.5.3 SIMD 与多线程的分工

| 层级 | 技术 | 适用场景 |
|------|------|----------|
| 指令级 | SIMD（AVX 等） | 内层循环紧密、连续内存的规则运算 |
| 线程级 | 多线程（`ForkJoinPool` 等） | 外层按行/块/样本划分的大粒度任务 |
| 节点级 | 分布式（MPI/Spark） | 数据规模超出单机内存 |

YiShape-Math 的线性代数实现（`RereDoubleMatrix` 等）在大规模运算时可利用多线程对子块调用高度优化的串行/SIMD 内核。

### 6.5.4 Java 平台上的实践要点

- **固定线程池**：避免无界创建线程，适合长时间运行
- **并行流**：语法简洁，但浮点累加顺序不固定，**结果可能因 JDK 版本与并行度略有差异**
- **少分配**：热路径上减少短生命周期对象，降低 GC 对并行效率的影响
- **`setParallelEnabled(boolean)`**：部分实现类提供开关，大矩阵时开启、小矩阵时关闭

> ⚠️ **JDK 25 + Vector API 的陷阱（2026 年现状）**
>
> YiShape-Math 的稠密线性代数内核使用 `jdk.incubator.vector` 的 SIMD 指令。**JDK 25 在不支持 AVX-512 的 x86 硬件上**会把 `DoubleVector.SPECIES_512` 报告为软件模拟（实测 lane 数仍是 8，但用 AVX2 拆 2 次执行），在某些工作负载下相对 `SPECIES_256` 反而**慢约 33 倍**。
>
> **建议**：在生产部署前，用真实矩阵规模对 `SPECIES_PREFERRED`、`SPECIES_256`、`SPECIES_512` 做一次基准；优先选择 `SPECIES_PREFERRED`（运行期根据 CPU 自动选最优 lane 数）。详见库内 `MEMORY.md` / `jdk25-species-512-software-emulation`。

### 6.5.5 并行调试与可重复性

1. **小矩阵上并行反而更慢**——线程开销超过计算收益，应以性能剖析为准
2. **并行归约顺序不同**可能导致末位浮点差异——科学复现需固定线程数
3. **并行不改变目标函数形状**——但若实现含随机采样，需记录随机种子
4. **内存带宽瓶颈**——计算强度不足时，多线程仍受内存墙限制

### 6.5.6 应用场景

| 场景 | 并行策略 | 预期加速 |
|------|----------|----------|
| 大规模最小二乘 | 梯度分块累加 | 接近核心数倍数 |
| 蒙特卡罗/Bootstrap | 独立抽样，尴尬并行 | 线性 |
| 交叉验证 | 各 fold 独立运行 | 线性 |
| 超参数网格搜索 | 各配置独立运行 | 线性 |
| L-BFGS 单次迭代 | 矩阵乘/分解并行 | 2-4×（受内存带宽限制） |

### 6.5.7 小结

- 并行**不改变问题的数学性质**，但改变常数因子和可重复性
- Amdahl 定律提醒：顺序瓶颈决定加速上限
- 小问题不并行，大问题优先并行线性代数内核
- 科学复现需记录并行配置（线程数、归约策略）

## 本节 API 一览

YiShape-Math **不提供** `Opts.parallel*` 之类的一键并行优化器，并行需要在调用方代码里组织。下面是真正可以用的钩子：

| 场景 | API / 实现 | 说明 |
|------|-----------|------|
| 矩阵运算并行开关 | `IMatrix#setParallelEnabled(boolean)` | 部分实现类提供；大矩阵开启，小矩阵关闭 |
| SIMD lane 选择 | `DoubleVector.SPECIES_PREFERRED` | 优先用 PREFERRED，让 JVM 选最佳；JDK 25 + 无 AVX-512 时**不要**硬编码 `SPECIES_512` |
| 多线程并行 | `java.util.concurrent.ForkJoinPool` / `ExecutorService` | 标准 JDK；用户负责任务拆分 |
| 多起点优化 | 用户层 for 循环 + `Opts.lbfgs().optimize(...)` | 见 6.4 节的多起点示例 |
| 交叉验证并行 | 用户层 fork-join，每 fold 独立调 `clf.fit(X_train, y_train)` | 与 ML 流程解耦 |

> ⚠️ **不存在的 API**：`Opts.parallelMinimize(...)`、`Opts.batchGradientDescent(...)`、`Opts.tuneThreads(...)`、`ML.fitParallel(...)`、`result.getHistory()`（应为 `result.getFunctionValueHistory()`）都未在公共 API 中提供。
>
> **并行收益**：计算量 $>10^6$ 次迭代时并行收益明显；< 1000 次迭代时线程开销可能抵消收益。

> ⚠️ **常见误区**：并行优化不是线程越多越好——超过 CPU 核心数后，上下文切换开销会抵消并行收益。对于计算密集型任务，线程数 = CPU 核心数是经验最优值。
## 本节小结

并行优化的核心问题是：如何利用多核 CPU/GPU 加速计算密集型任务。数据并行通过将数据划分为多个子集，让各线程独立处理；任务并行将不同任务分配给不同线程；模型并行将大模型分片存储和计算。

**核心要点**：
- Amdahl 定律：加速比上限取决于串行部分的比例
- 线程安全是并行代码的核心挑战——共享状态需要锁保护
- ExecutorService 是 Java 标准并行框架
